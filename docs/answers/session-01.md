# پاسخ سوالات تشریحی درس اول

## سؤال ۱ — Constitution و حاکمیت معماری

تیم شما تصمیم گرفته تمام Business Logic در لایهٔ Domain یا Application قرار بگیرد و API فقط مسئول دریافت درخواست و ارائهٔ پاسخ باشد.

Coding Agent یک قابلیت را پیاده‌سازی کرده و همهٔ Testها موفق شده‌اند؛ اما بخشی از Business Logic مستقیماً داخل Controller یا Endpoint نوشته شده است.


- چه تفاوتی بین موفقیت Testها و رعایت اصول معماری وجود دارد؟

لزوما پاس شدن تست‌ها به معنی درست بودن رعایت اصول معماری یا درست بودن پیاده سازی نیست.
تو تست‌ها معمولا رفتار مورد انتظار اون واحد رو بررسی می‌کنیم، اما در اصول معماری نحوه پیاده‌سازی، جداسازی بخش‌ها و مسئولیت‌ها و قابلیت نگه‌داری و اسکیل بودن پروژه در نظر گرفته میشه

مثلا تو تست ممکن هستش که یک متد داخل کنترل مواردی مثل اعتبارسنجی، اجرا منطق بیزینس و تغییر وضعیت رو انجام بده و تست‌های اون هم پاس بشه، اما اصول معماری مثل تفکیک مسئولیت‌ها تو این مثال رعایت نشده و اصول نقض شده.

- قاعده جداسازی مسئولیت‌ها باید در Constitution، Plan یا Tasks ثبت شود؟ چرا؟

منطقا این قاعده تو مرحله اول باید Constitution ثبت بشه، چون جداسازی لاجیک و منطق بیزینس از API یک اصل معماری و همیشگی تو پروژه هستش.
constituion : قوانین اصلی معماری
plan : نحوه اعمال قانون در طراحی فیچرها
task: اقدامات اجرایی برای رعایت قانون


- چگونه می‌توان در توسعه‌های بعدی از تکرار این مشکل جلوگیری کرد؟

این که صرفا قانون رو تنها داخل constituion بنویسیم کافی نیستش و باید در چند قسمت دیگه هم در حین توسعه کنترل رو داشته باشیم
* به صورت صریح تو constitution ثبت کنیم
* بررسی رعایت ساختاری تو کدریویو
* از agent بخواهیم قبل از توسعه constitution و implement روی بررسی کنه (معمولا از طریق agents.md)


## سؤال ۲ — Specify و Clarify
مالک محصول می‌گوید:

«کارمندان بتوانند درخواست ثبت کنند و مدیرها بعد از بررسی، درخواست‌ها را تأیید کنند.»

Coding Agent فرض می‌کند هر مدیری می‌تواند درخواست خودش را نیز تأیید کند.



- آیا Agent مجاز است این تصمیم را بدون تأیید مالک محصول نهایی کند؟

نه چون این موضوع یک تصمیم محصولی هستش و ایجنت می‌تونه پیشنهاد بده ولی تصمیم نهایی و اصلی رو باید مالک محصول بگیره

- تفاوت Assumption با تصمیم تایید شده مالک محصول چیست؟

assumption یک فرضی هستش که به خاطر نبود اطلاعات کافی و برای اینکه پند نشیم گرفته میشه، اما تصمیم تایید شده یک تصمیمی هستش که یک مالک محصول با بررسی جنبه‌های مختلف اون رو گرفته و مسئولیت اون تصمیم با مالک محصول هستش


- حداقل دو ابهام مهم دیگر در این درخواست پیدا کنید.

* هر مدیر چه درخواست‌هایی رو می‌تونه بررسی کنه؟ درخواست‌های تمام سازمان یا درخواست‌های واحد و تیم خودش
* آیا امکان برگشت درخواست برای اصلاح وجود داره یا نه؟ اگه وجود داره چه اطلاعاتی رو درخواست دهنده می‌تونه ویرایش کنه؟

- کدام ابهام‌ها باید در Specify برجسته شوند و Clarify چه نقشی در رفع آن‌ها دارد؟

تو مرحله specify باید نیازمندی‌ها و محدودیت‌ها و همچنین رفتارهایی که مد نظرمون هستش رو مشخص کنیم و هر جا اطلاعات ارائه شده برای تعریف رفتار کافی نبود، باید اون اطلاعات ناقص و ابهام ها رو شناسایی کنیم و مستندشون کنیم و تو مرحله clarify اون‌ها رو بررسی کنیم و بعد از دریافت پاسخ از مالک محصول تصمیم نهایی رو بگیریم و ثبت کنیم


## سؤال ۳ — Requirement در برابر Design Decision

در Specification آمده است:

«هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا شود.»

توسعه‌دهنده پیشنهاد می‌کند یک فیلد عددی به نام ContentRevision اضافه کنیم.

− کدام بخش Requirement است و کدام بخش Design Decision؟

بخش «هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا شود.» یک requirement هستش، چون رفتار و محدودیت رو مشخص کرده اما در باره پیاده سازی تصمیمی نگرفته
و بخش پیشنهاد توسعه دهنده یک design Decision هستش چون روش پیاده سازی فنی اون نیازمندی رو پیشنهاد داده

− چرا بهتر است مکانیزم فنی در Plan/Research بررسی شود؟

به این خاطر که ممکن هستش که برای یک نیازمندی چندین راهکار فنی وجود داشته باشه و باید از قبل و براساس محدودیت‌ها و پیچیدگی ها و ... تصمیم نهایی رو بگیریم

− حداقل دو راهکار جایگزین برای تشخیص محتوای تأییدشده پیشنهاد کنید و Trade-off آن‌ها را توضیح دهید.

* **پیاده سازی ورژن نامبر**

با هر تغییری که میدیم یه نسخه پیش نویس از اطلاعات تایید شده رو داشته باشیم و بعد از تایید اطلاعات پیش نویس جایگزین اطلاعات اصلی بشه

**مزایا:**

پیاده سازی آسان و ساده
مقایسه سریع

**معایب:**

حجم ذخیره سازی اطلاعات به مرور افزایش پیدا می‌کنه

تو اسپرینگ بوت میشه از @Version در JPA استفاده کرد

---

* **استفاده از Content Hash**

از محتوای درخواست یک Hash مانند SHA-256 تولید می‌کنیم و مقدار آن را هنگام تأیید ذخیره می‌کنیم.
هنگام اجرای درخواست، مجدداً Hash محتوای فعلی محاسبه و با مقدار ذخیره‌شده مقایسه می‌شود.

**مزایا:**

تشخیص تغییر محتوا حتی در صورت تغییر خارج از مکانیزم Version
عدم وابستگی به شماره نسخه
مناسب برای اطمینان از یکسان بودن محتوای تأییدشده و محتوای اجراشده

**معایب:**

نیاز به تعریف دقیق فیلدهایی که در محاسبه Hash دخیل هستند.
تغییر در نحوه Serialization اطلاعات می‌تواند روی Hash تأثیر بگذارد.
محاسبه Hash به‌تنهایی تاریخچه تغییرات را نگهداری نمی‌کند.


## سؤال ۴ — Tasks و Analyze

برای یک Feature، تعداد ۳۰ Task تولید شده و هر Requirement حداقل به یک Task مرتبط است. با این حال، یک Task به دیتابیس آماده نیاز دارد، در حالی که Migration دیتابیس در Task بعدی تعریف شده است. همچنین دو Task دارای نشانگر [P] باید فایل مشترکی را تغییر دهند.


- چه مشکلاتی در Dependency و Parallelism وجود دارد؟

مشکلی که الان وجود داره این هستش که ترتیت اشتباهی تو دپندنسی‌ها وجود داره، چون اول باید migration دیتابیس انجام بشه و بعد تسک انجام بشه
همچنین برای تسک‌هایی که نشانگر P دارند هم نشون دهنده این هستش که parallelism به درستی انجام نشده، چون که هر دو تسک می‌خواهند یه فایل مشترک رو تغییر بدن، ممکن هستش که کانفلیکت اتفاق بیفته و بهتر هستش که اول یکی از تسک‌ها انجام بشه و بعد تسک بعدی انجام بشه یا اینکه تغییرات فایل مشترک تو یه تسک تجمیع و انجام بشه

- انتظار دارید Analyze چه Findingهایی گزارش کند؟

* نیازمندی‌های تسک : نیازمندی‌های یک تسک قبل از اجرای اون تسک آماده بشه
* کانفلیکت‌های اجرای موازی : تسک‌هایی که اجرای موازی اون باعث کانفلیکت میشه، شناسایی بشن
* ترتیب اجرا تسک‌ها : ترتیب تسک‌هایی که درست نیست، شناسایی و گزارش بشه
* ریسک‌های احتمالی برای پیاده سازی : ریسک‌هایی احتمالی که برای اجرا ناقص یا کانفیلیکت تسک‌ها وجود داره، شناسایی و گزارش بشه

همچنین ارتباط بین نیازمندی‌ها و تسک‌ها و تصمیمات طراحی بررسی بشه که آیا تسک‌ها اون‌ها رو پوشش میده یا نه

- آیا پوشش ۱۰۰٪ Requirementها توسط Tasks، آمادگی قطعی برای Implement را ثابت می‌کند؟ چرا؟

نه، صرفا مشخص می‌کنه که برای هر نیازمندی حداقل یه اقدام اجرایی داریم ولی این مورد تضمین کننده صحت طراحی نیستش
مثلا ممکنه که تسک‌ها وابستگی اشتباه داشته باشند یا اینکه تسک‌ها با تصمیم‌های طراحی سازگار نباشن


## سؤال ۵ — Implement، Validation و Converge

Coding Agent گزارش داده است:

«تمام Taskها تکمیل شده‌اند؛ پروژه Build شده و ۱۲۰ Test همگی Passed هستند.»

اما در Code Review متوجه می‌شوید یک قاعدهٔ امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز ارزیابی نشده است.

- آیا Feature قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است؟

نه، این گزارش صرفا اعلام می‌کنه که پروژه به درستی بیلد میشه و خطای سینتکسی نداریم، اما ممکنه یه سری فیچر به درستی پیاده سازی نشده باشن

- تفاوت Build، Test، Validation و Acceptance چیست؟

**بیلد:** یعنی اینکه برنامه از نظر کد و وابستگی‌های فنی قابلیت تبدیل به فایل اجرایی رو داره یا نه

**تست :** رفتار بخش‌های مختلف سیستم رو دربرابر سناریوهایی تعریف شده، بررسی می‌کنه

**ولیدیشن:** پیاده سازی انجام شده با محدودیت‌ها و معیارها مورد انتظارمون مطابقت داره یا نه. مواردی مثل تست اتومات، بررسی امنیتی و ...

**acceptance:** اون تایید نهایی که مسئول اون بخش انجام میده که آیا این فیچر و پیاده سازی نیازمندی رو برطرف کرده یا نه

- Converge در این وضعیت چه نقشی دارد و چه تفاوتی با Analyze دارد؟

هر دو مورد کیفیت و سازگاری کاری که انجام شده رو بررسی می‌کنه، اما هدف متفاوتی دارند
آنالیز قبل از پیاده سازی انجام میشه و هدفش بررسی  این هستش که طراحی و برنامه اجرایی ما منطقی و کامل هستند یا نه.
کاوریج بعد از پیاده سازی و ولیدیشن انجام میشه و هدفش بررسی فاصله بین وضعیت واقعی کد و موارد مستند شده هستش

- اگر Converge شکاف جدیدی پیدا کند، مسیر اصلاح چیست؟

باید اون شکاف بررسی و تبدیل به یک تسک مشخص بشه
